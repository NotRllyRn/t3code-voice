# Experimental Voice releases and upstream automation

This fork uses `U-voice.R`: `U` is a pinned, stable upstream version and `R` is a positive Voice revision. For example, `0.1.9-voice.1` → `0.1.9-voice.2` → `0.1.10-voice.1`. The pin and channel policy live in [`forkIdentity.ts`](../../packages/shared/src/forkIdentity.ts). Voice versions are SemVer prereleases, not build metadata. The current experimental channel requires GitHub `prerelease: true`; changing that policy needs a reviewed consumer compatibility change. It does not mean upstream stable releases belong in a Voice feed.

Only the exact installed `0.1.9-preview.20261116.1` preview is an allowed legacy current version. Desktop downloads are manual; the ARM64 DMG selector is not an Electron ZIP/feed updater. macOS private self-signing is not Apple-trusted Developer ID signing or notarization. This release targets macOS and its matching server/web client. Fork mobile/iOS work is deferred; upstream mobile source is retained.

## Build-only evidence, not publication

After a reviewed merge to the configured Voice integration branch, `voice-build.yml` accepts the exact merge SHA, PR number and reviewed head SHA. It verifies the merged PR identity and source ancestry in `VOICE_BUILD_BASE_BRANCH`; missing configuration fails closed. Register this workflow on the default branch and restrict the `voice-build` environment to that exact branch before enabling it. Set `VOICE_BUILD_ENABLED` and `VOICE_BUILD_BASE_BRANCH` in that environment only. All four release package manifests must match the configured Voice version; the build never rewrites source. Environment reviewers make each build supervised; unattended builds require protected workflow/base branches with enforced checks, current-head approvals and no automation bypass. Do not add failing required checks merely to enable automation: establish working checks first.

Hosted Mac artifacts use ad-hoc signing and are not equivalent to persistently signed Maya releases or an upgradeable Mac feed. No signing key is copied to GitHub. A proper signed release still uses the existing Maya release process.

The lane builds Linux x64 server archives and macOS ARM64 DMG/ZIP artifacts afresh, with a smoke check for each. It retains workflow artifacts for 14 days, named with version, full source SHA and target. Each target carries `voice-release.json`, `SHA256SUMS`, and upstream notes followed by `## Voice Fork`. The descriptor records the source/upstream pins, registered database migration head, orchestration protocol version, final-byte SHA-256/size, target and experimental trust state. Per-target descriptors are build evidence, not a combined public release manifest or update feed. Publication would need a separately reviewed aggregation step that rejects mismatched versions/source pins, plus explicit approval. No release, tag, npm publication, deployment or installation runs here.

The inherited upstream release pipeline remains gated. This lane does not pass the inherited `--skip-build` flag, which the fork packager correctly refuses. Native build success, artifact retention, macOS trust, real installation/update and rollback must be evidenced separately; a checksum or successful unit test is not that proof. Hosted runner availability and macOS billing limits must be checked on the account.

## Signed upstream updates (disabled until configured)

`voice-upstream-watch.yml` checks the latest stable release every six hours when installed on the default branch and enabled. It rejects drafts, prereleases, moved tags, commits outside upstream `main`, and releases not descending from the accepted pin. Main commits alone do not trigger work. The receiver independently repeats the GitHub checks; release notes never become instructions.

Precreate and verify the `voice-automation` environment before registering/running the workflow, even before storing secrets; otherwise GitHub can implicitly create an unprotected environment. The `voice-automation` environment must restrict deployments to the exact default branch (branch rule only, no tags). Verify the saved deployment policy before adding secrets; an environment name or pinned checkout alone does not protect secrets from modified branch workflows. Protect the default branch against direct/force pushes and require reviewed PRs and passing checks. Required environment reviewers pause every poll; unattended polling instead needs these branch protections and a one-time activation approval. If those controls are unavailable, keep reviewer approval and describe polling as supervised.

The protected `voice-automation` environment must set `VOICE_UPSTREAM_SOURCE_SHA` to a reviewed full sender commit containing the bounded release-response fix and the currently accepted upstream pin. Advance this SHA after every accepted upstream update; otherwise the sender keeps proposing an already accepted release. The workflow checks out that immutable source, independently of the receiver's approved worktree base. An unset source SHA produces a notice and skips checkout/poll/delivery; a malformed nonempty SHA fails closed. A manual send request while delivery is disabled produces a notice. Manual dispatch on the default branch defaults to a read-only poll; `send_webhook: true` requests delivery only while `VOICE_UPSTREAM_WATCH_ENABLED` is `true`. Set that switch in the `voice-automation` environment, without a repository/organization variable of the same name. The send step evaluates it after environment variables are available, for both scheduled and manual runs; unset or false disables all delivery. Read-only manual polling remains available. Public GitHub API requests are unauthenticated and can hit shared-runner rate limits; an HTTP rate-limit failure stops the run without delivery and must not be reported as a successful no-op. GitHub must first register the workflow on the default branch before branch dispatch or scheduled runs are available. An unchanged latest release is a successful no-op, not an end-to-end launch test; do not reset the accepted pin to manufacture a candidate.

The existing T3 scheduler's signed `voice-upstream-release` action calls the app's thread-launch service. It creates one ordinary top-level thread in the server sidebar, with a new isolated worktree from the explicitly configured local `baseBranch` (`startFromOrigin: false`). That branch must contain `acceptedSource`, a full approved integration commit. The receiver resolves the exact base commit before claiming and persists it in the launch; preparation and recovery reject a missing or moved branch instead of fetching or falling back. The PR target is the same configured branch. The current project/environment default model selection must name an enabled Codex instance. Its model and options are read at dispatch, using normal configured provider authentication. There is no dedicated provider, credential bridge, or external executor.

Before activation:

1. Confirm the upstream repository/release policy and intended local Voice base branch. The current policy is `pingdotgg/t3code`, stable `vMAJOR.MINOR.PATCH` tags on `main`, targeting `NotRllyRn/t3code-voice`. Keep the local base current through reviewed integration. Confirm Codex's project default selection, provider access, and GitHub permission to push branches and open PRs.
2. Confirm the project has no setup scripts (including inherited scripts), `autoPull: false`, and `defaultAutoPull: false`. Worktree preparation must not run setup or link an environment file.
3. Create a disabled webhook task bound to a visible coordinator thread using the supported scheduler API: `schedule: {type: "webhook", action: "voice-upstream-release", signature: {header: "x-hub-signature-256", encoding: "hex", prefix: "sha256=", secretRef}, maxDeliveryAgeMinutes: 5}`. Omit scheduler `dedupe`; the action owns durable release claims. Obtain the user's signing secret through `request_secret`, never chat or command arguments. The normal webhook HMAC, generation, replay, rate-limit and auth controls remain in force.
4. Configure the owner-only (`0600`) `voice-webhook-action.json` in the server secrets directory with `enabled`, `action`, `launchPolicy: "configured-codex-v1"`, `baseBranch: "<intended-local-integration-branch>"`, `acceptedSource: "<approved-40-character-source-SHA>"`, the exact task ID/current generation, project ID, coordinator `managerThreadId`, and an owner-only (`0700`) `stateDir` outside the checkout and T3 home. Enable the task only when ready, then bind its new generation. The server also requires `VOICE_AUTOMATION_ENABLED=1` in its process environment; changing a service definition does not enable an already-running process. Plan any required restart separately with the server owner. No setup is performed automatically.
5. Configure the returned managed HTTPS webhook URL and matching signing secret in GitHub's protected `voice-automation` environment as `VOICE_UPSTREAM_WEBHOOK_URL` and `VOICE_UPSTREAM_WEBHOOK_SECRET`. If no public URL is available, configure supported T3 remote access first. Keep `VOICE_UPSTREAM_WATCH_ENABLED` off until receiver configuration and permissions have been checked.

A successful claim allows one active update and at most one launch in 24 hours. Duplicate deliveries and tags cannot create another thread. A crash or uncertain launch remains claimed for manual reconciliation; inspect the visible thread/worktree before changing state, and never clear replay history merely to retry. The two-hour prompt deadline is not a hard runtime or spending cap; no standalone supervisor is installed. Use ordinary T3 stop controls and reconcile the claim before another update.

The thread receives ordinary top-level MCP capabilities from its configured provider, not the coordinator’s narrower client grants. The following merge/deploy restrictions are prompt instructions, not capability enforcement.

The update thread tests changes and inspects its diff, title and body before opening/linking a PR. It may merge the exact reviewed head only after enforced required checks and current-head approvals pass, with no unresolved findings or conflicts. Changed head/base evidence requires retesting and fresh review. Missing protection, failed checks, unresolved conflicts or the task deadline stop work for manual reconciliation. The thread then dispatches the artifact-only workflow for the confirmed merge SHA. It never publishes releases/packages, deploys, installs or restarts services. GitHub branch protection enforces merge safety; prompt instructions alone are not an authorization boundary. Offline checks do not prove provider execution or GitHub access; activation requires those operator prerequisites.

### Retired Pi automation

Old bindings without `launchPolicy`, `baseBranch`, or `acceptedSource` are refused and require explicit reconfiguration. Old clean-constrained launches/replays and provider sessions are rejected. Queued work and restart continuations whose thread history contains a clean constraint fail before provider startup; create a new ordinary thread explicitly instead of resuming them unrestricted. Historical constraint decoding remains only for retirement compatibility. Normal upstream Pi and stored provider-secret loading remain available. Pause old scheduler tasks and reconcile any old active claim before enabling the Codex action.
